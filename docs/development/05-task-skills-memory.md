# 05 — TaskManager、需求澄清、SkillOpt 与九层记忆

## 1. 共同原则

这四类功能容易变成“设置页里存在、任务里感觉不到”的装饰。KnightFrame 采用共同规则：

- TaskManager 默认开启；
- Caveman Lite 默认开启；
- Skill 本地关键词路由默认开启；
- 记忆存储默认关闭；
- Skill/记忆的副模型判断分别默认关闭；
- 长文本澄清询问由本地字符计数触发，零模型费用；
- 只有真正选中的内容进入主模型动态尾部；
- 每次触发都有本地回执、效果和 token 统计；
- 主模型不能写记忆库。

## 2. TaskManager

### 2.1 定位

TaskManager 是运行时状态机，不是第二个 agent，也不是每轮额外模型调用。它负责让用户始终知道：

- 当前目标；
- 正在做什么；
- 已完成什么；
- 下一步是什么；
- 是否失败、取消或被阻塞；
- 本任务消耗了多少时间、token 和费用。

### 2.2 默认行为

每条被接受的用户请求建立或更新 Task：

```text
New -> Clarifying? -> Ready -> Running -> Verifying -> Done
                                      -> Blocked
                                      -> Failed
                                      -> Cancelled
```

普通问答可作为单步 Task，回答完成即 Done。代码任务在项目速查 Ready 后进入 Running。

关闭 TaskManager 时，运行时仍保留必要的 Turn 状态用于可靠执行，但不向主模型提供 `task` 工具、不显示计划面板、不维护跨 Turn 目标。关闭行为不影响会话和工具正确性。

### 2.3 `task` 工具

模型可见 schema 保持极短：

```text
task { op:"plan", steps:["定位","修改","验证"] }
task { op:"done", step:1 }
task { op:"block", reason:"需要用户选择 API" }
task { op:"revise", steps:[...] }
```

规则：

- runtime 已自动建立 goal，不要求模型复述用户长请求；
- 多步骤任务应在首个项目查询时并行提交 `plan`，不为计划单独等待；
- 同时只允许一个 `in_progress` 步骤；
- 工具开始/结束自动挂到当前步骤；
- edit 成功、测试通过等事实由 runtime 自动结算，不靠模型声称；
- `done` 只代表模型认为步骤完成，最终状态需结合工具与验证事实；
- 阻塞必须给用户可行动的原因，不允许用“任务很难”冒充阻塞。

### 2.4 UI 回执

默认采用紧凑顶部进度或可展开任务卡：

- 当前步骤；
- 已完成/总步骤；
- 运行/验证/阻塞状态；
- 取消；
- 展开后显示工具、文件变更和验证证据；
- 完成后形成可回查的小票。

TaskManager 信息不重复出现在最终回答中；回答只总结最重要结果。

### 2.5 指标与验收

- Task 创建率、完成率、取消率、阻塞率；
- 计划实际修改次数；
- 无工具证据却被标完成的次数，目标为 0；
- 主任务等待后台任务的时间；
- TaskManager 增加的工具 schema 与调用 token；
- 崩溃重启后状态恢复；
- 用户 steer 后旧计划被修正且历史保留；
- Windows 进程取消后 Task 必须落到明确终止状态。

## 3. 长文本需求澄清（GrillMe）

### 3.1 精确触发

每一条用户文本请求在发送前由本地 UI 计算长度。定义：

- 对首尾空白裁剪后的 Unicode grapheme cluster 计数；
- 内部空格、换行、标点和代码均计入；
- 图片、音频等非文本附件本身不计入；用户粘贴或附件提取出的文本计入；
- 条件是严格 `count > 200`，200 不触发，201 触发；
- 检测不调用任何模型。

触发后，先弹出资源键对应的确认：

```text
zh-CN: 检测到大量文本信息，要开启需求澄清吗？
en-US: A large amount of text was detected. Enable requirement clarification?
```

句子存放在 locale catalog，不能直接写在组件中。

### 3.2 用户选择

- **开启**：Task 进入 `Clarifying`，主模型进入澄清模式；
- **不开启**：原请求立即按正常流程执行；
- **取消发送**：返回编辑器，文本不丢失；
- 该选择只作用于当前请求，不暗中改变全局设置。

### 3.3 澄清模式

澄清由主模型完成，不默认调用副模型：

- 一次只问一个问题；
- 每个问题附一个推荐答案及简短取舍；
- 在写文件、运行破坏性工具或开始实现前至少完成 3 个实质问题；
- 用户可随时选择“信息足够，开始执行”；
- 已能从项目速查或设置发现的答案不再询问用户；
- 每个答案直接更新 Task 的目标、约束或非目标；
- 澄清结束时生成紧凑需求合同，用户可检查后执行。

“需求澄清”和“需求压缩副模型”是两个独立功能：前者解决歧义，后者只降低长输入进入主模型的 token。

### 3.4 回执与验收

- 201 grapheme 中英文/emoji/组合字符 fixture 均触发；
- 200 不触发；
- 开启前没有项目写操作；
- 一次只显示一个问题；
- 推荐答案可见；
- 跳过后立即继续；
- 触发率、开启率、澄清轮数、澄清后需求变更和额外 token 可度量；
- 中英文资源键、占位符和无障碍标签完整。

## 4. Skill 系统

### 4.1 目标

Skill 是按需加载的行为说明，不是每轮常驻知识库。主模型只看到当前任务真正需要的少量 Skill；完整目录始终留在本地。

### 4.2 Skill 包

建议兼容以 `SKILL.md` 为入口的目录：

```text
skill-name/
  SKILL.md
  references/
  scripts/
  assets/
```

索引字段：

- name、description；
- 中英文关键词和显式 triggers；
- 平台、语言、文件类型；
- 所需工具/权限；
- 是否允许模型自动触发；
- 正文与资源大小；
- 来源、版本和兼容等级。

### 4.3 兼容等级

对 Claude/Codex 等 Skill 字段逐项声明：

```text
Supported     字段有真实执行行为
Degraded      可解析，但部分语义缺失并明确提示
Unsupported   拒绝安装或禁用相关能力，绝不静默忽略
```

例如 `allowed-tools`、hook、动态命令、context fork、supporting files 必须各有实现或明确降级。解析成功但不执行视为缺陷。

### 4.4 默认本地路由

每个 Turn 开始冻结一代 Skill catalog，流程：

```text
平台/依赖/权限确定性过滤
  -> 用户明确点名的 Skill 固定入选
  -> 本地关键词、任务类型、语言、文件类型排序
  -> 选择极少候选
  -> 只注入入选 Skill 正文
```

规则：

- 中文短词采用 FTS + 子串；
- 正文不进入索引排序 prompt；
- 同一 Turn 内安装/更新的新 Skill 下一 Turn 才生效；
- supporting files 由 Skill 指令按需 `read`；
- host 绝对路径不进入 prompt；
- 无命中时不注入任何 Skill 容器或空名单。

### 4.5 可选副模型路由

用户单独开启 `SkillSelector` 后：

- 本地逻辑仍先筛候选；
- 副模型只看候选名称、短描述和当前请求；
- 返回入选短 ID；
- 失败回退本地排序；
- 每 Turn 最多一次；
- 必须显示额外费用、延迟和相对本地选择的变化。

### 4.6 Caveman Lite

Caveman 是内置输出 Skill，默认 `Lite`：

- 删除客套、填充、重复结论和不必要保留意见；
- 不牺牲警告、验证结果、路径、代码和用户要求的细节；
- `Off` 完全关闭；未来可保留 `Full`，但不得默认；
- 它不参与普通 Skill 路由，不需要每 Turn 匹配；
- 运行时只向稳定前缀加入当前 locale 的一条短风格规则；
- UI 的实际输出长度、用户展开/追问率用于证明它确实生效。

这样保留“Caveman Skill 默认 Lite”的产品语义，又避免注入整个 Skill 文件。

## 5. SkillOpt

### 5.0 第一阶段运行时实现

Rust 运行时的最小实现遵守以下边界：

- 旧 `agent-standalone` 的 34 个内置 Markdown Skill 在编译时嵌入 EXE，不依赖旧目录；
- 每个 Turn 只在本地扫描元数据并冻结一代 catalog，正文不参与模型路由；
- 来源优先级为项目、用户、内置，项目同名 Skill 覆盖用户和内置版本；
- 用户状态读取 `~/.knightframe/skill-states.json`，项目状态读取 `<workspace>/.knightframe/skill-states.json`，项目状态优先；
- 最多选择 3 个 Skill（包含 companion），只有被选中的正文进入当轮动态尾部；
- 未匹配时不生成 Skill 消息、空容器或模型调用；`SkillSelector` 仍保持关闭；
- `Caveman` 文件只用于 catalog 兼容，实际 Lite 行为继续由稳定前缀中的短规则提供；
- 旧工具名通过当轮 host compatibility 合同映射到 `find/search/read/edit/run/task`；不可执行字段在 catalog 和 receipt 中标为 `degraded`，不会静默声称支持；
- `skill.activated` receipt 包含 catalog generation、来源、版本、选择原因、兼容等级、注入字节和估算 token；
- SkillOpt 第一阶段只累计本地命中次数、注入字节并产生确定性索引/拆分建议，不调用模型、不自动改文件。

后端 IPC 提供 `kf_skill_catalog` 和 `kf_skill_set_enabled`。它们是后续 Skill 管理页面的真实数据源，不要求主模型持有 Skill 列表。

### 5.1 定位

SkillOpt 是本地低频优化器，不是另一个每轮路由模型。它分析真实使用回执，提出 Skill 索引和内容改进建议。

### 5.2 输入

- 本地路由命中与未命中；
- 主模型实际是否遵循该 Skill；
- 用户手动更换/关闭 Skill；
- Skill 注入 token；
- 任务成功、失败与重试；
- 中英文查询覆盖；
- 冲突和重复描述。

它不需要项目源代码、完整会话或模型隐藏推理。

### 5.3 输出

```text
新增/删除关键词建议
description 缩短建议
冲突 Skill 合并建议
误触发/漏触发报告
长期未执行字段报告
```

所有建议先进入 UI 审核；默认不自动改 Skill。确定性统计是默认实现。未来若用户为 SkillOpt 显式配置副模型，也只能离线生成建议，不进入主任务热路径。

### 5.4 存在感

Skill 页面必须显示：

- 最近触发次数；
- 实际采用率；
- 注入 token；
- 任务成功关联；
- 误触发/漏触发；
- 当前优化建议及采纳结果。

如果某 Skill 从未触发、字段从未执行或无法度量，UI 必须标明，而不是显示“已启用”。

## 6. 九层长期记忆

### 6.1 默认关闭

记忆存储默认关闭。关闭时：

- 不创建记忆库；
- 不扫描会话生成候选；
- 不加载 MemoryJudge；
- 不向主模型注入记忆说明或工具；
- UI 仅在设置/功能发现页提供开启入口；
- 不产生任何记忆模型调用或外发。

### 6.2 主模型边界

主模型：

- 没有记忆写工具；
- 不能浏览记忆库；
- 只在运行时判定需要时读取已选的少量记忆；
- 收到的是正文、层级和来源，不收到内部打分或长 ID；
- 最终回答不能暗中写回记忆。

### 6.3 写入来源

第一阶段只接受用户可审计来源：

1. 用户使用“记住”操作或 `/remember`，本地提取明确选择的文本并请求确认；
2. 用户在记忆页面手动新增、编辑、导入；
3. 用户选择从旧 KnightFrame 迁移，经预览后导入。

不自动从每轮对话抓取，不让主模型决定保存什么。这样避免把错误回答、瞬时状态和敏感内容永久保存。

### 6.4 九层定义

保留旧工程九层语义，删除 16 维坐标：

| 层 | 中文 | English | 内容 |
|---:|---|---|---|
| L0 | 感知 | Perception | 一次明确观察或原始事实 |
| L1 | 情节 | Episode | 带时间/任务上下文的事件 |
| L2 | 语义 | Semantic | 稳定概念、项目事实或偏好 |
| L3 | 模式 | Pattern | 多次出现的可复用规律 |
| L4 | 原则 | Principle | 解释取舍的长期原则 |
| L5 | 方法 | Method | 可重复执行的过程 |
| L6 | 规则 | Rule | 明确应做/不得做的操作规则 |
| L7 | 公理 | Axiom | 很少变化的基础假设 |
| L8 | 准则 | Canon | 产品/身份级最高约束 |

深度不是相关度。L8 与当前请求无关时不能因为“更深”而注入；L0 精确命中时可以优先。

### 6.5 层级写入与晋升

- 新的明确观察默认建议 L0；
- 用户可直接选择任何层并看到解释；
- 本地逻辑可根据同关键词、项目、来源和重复次数产生“晋升候选”；
- 本地逻辑不凭空改写多条记忆为抽象原则；
- 晋升、合并、冲突解决和删除都需用户确认；
- 第一阶段不使用 LLM 自动合成深层记忆；
- 每层均有独立列表、筛选、读写/命中统计和验收 fixture，不能只是一个数字标签。

### 6.6 默认本地读取判断

记忆开启、MemoryJudge 关闭时：

```text
当前请求
  -> 本地关键词/实体/项目/scope 匹配
  -> 未达门槛：不查、不注入
  -> 达到门槛：取少量候选
  -> 去冲突、过期和重复
  -> 按 token 预算注入主模型动态尾部
```

默认最多 3 条；实际预算以模型和任务为准。无命中时不注入“memory empty”说明。

### 6.7 可选 MemoryJudge

用户显式启用后：

1. 副模型只看当前用户请求；
2. 只输出 `needed` 和极短检索词；
3. `needed=false` 时结束，不访问记忆内容；
4. `needed=true` 时由本地索引检索；
5. 副模型不看完整记忆库、不写记忆；
6. 失败回退本地关键词路径。

该模式每 Turn 最多一次，并显示调用费用、延迟、判定和最终实际注入数。

### 6.8 记忆回执

当轮紧凑回执：

```text
记忆：使用 2 条 · L2/L6 · 126 tokens
```

展开后显示：

- 哪些记忆；
- 匹配原因；
- 层级、scope、来源；
- 是否被主模型引用到最终行动；
- token；
- 本地或副模型判断；
- 用户可禁用、编辑或删除。

回执只在 UI/事件账本，不回灌 prompt。

### 6.9 Scope 与隐私

至少支持：

```text
global      用户跨项目偏好
workspace   当前项目事实与规则
session     只在当前会话有效，不属于长期存储
```

项目记忆不得跨项目注入。导出、删除、清空和彻底遗忘必须可验证。外置 MemoryJudge 只发送当前请求，不发送记忆内容；本地副模型不外发。

### 6.10 验收

- 关闭后数据库、模型调用、prompt 注入严格为 0；
- 九层各自完成新增、检索、回执、编辑、删除 fixture；
- scope 隔离无串项目；
- 主模型协议中不存在 memory write；
- 默认本地关键词路径可处理中英文；
- MemoryJudge 开启/关闭路径独立；
- 无关深层记忆不会因层级高而注入；
- 每条注入可追溯、可一键撤销；
- 16 维坐标、神经图和无形的自动融合不进入新实现。

## 7. 共同指标

| 功能 | 效果 | 成本/延迟 | 失败/退化 |
|---|---|---|---|
| TaskManager | 完成率、验证覆盖 | schema/call token、等待 | 错误完成、恢复失败 |
| GrillMe | 澄清后返工下降 | 额外轮次/token | 误触发、用户取消 |
| Skill | 采用率、任务增益 | 注入 token | 误触发、未执行字段 |
| SkillOpt | 建议采纳后的改善 | 后台时间/可选费用 | 无收益、建议被撤销 |
| Memory | 检索精度、实际引用 | 注入/副模型 token | 串 scope、冲突、过期 |

任何功能若连续版本没有真实触发、没有可见回执或无可测收益，应从正式产品移除，而不是继续作为卖点保留。
